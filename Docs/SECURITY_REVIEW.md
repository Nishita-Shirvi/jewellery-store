# Security review — Week 3 (Phase 23)

**Date:** 2026-11-03 · **Branch:** `week3-growth` · **Scope:** every server action, API route, admin page and customer page in the repo, plus dependencies.
**Method:** an independent read-only review (traced each action from form to database query), followed by fixes, automated tests for each fix, and "break it on purpose" checks proving each test catches a regression.

**Result:** no Critical or High findings remain in the application. Two Medium and four Low findings were found; all are fixed except two Lows that are accepted (below). One Critical dependency advisory (Next.js) was fixed by a patch upgrade.

## New protections added in Phase 23

- **Account lockout:** 8 wrong passwords → that account is locked for 15 minutes (the right password is refused too); a successful login resets the count. Unknown emails behave like wrong passwords, so the lock message doesn't reveal which emails have accounts.
- **Password reset:** "Forgot your password?" on the login page. Same answer whether or not the email exists; 3 requests/hour per email, 10/hour per IP. The link is valid for **30 minutes, once**; only a hash is stored; a newer request cancels older links; two uses at the same moment → only one succeeds. Resetting unlocks the account.
- **Sessions:** last 14 days (was 30); changing the password signs out every other device within 5 minutes. The admin area no longer trusts the role in the cookie — the database is checked on every admin page and action.
- **Finished background jobs keep no payload,** so one-time links in emails don't linger in the database.

## Accepted risks (and why)

- **Someone can deliberately lock a customer's account** by entering wrong passwords 8 times from several IPs. The customer can still get in immediately with "Forgot your password?" (which clears the lock). This is the usual trade-off: without a lock, passwords could be guessed.
- **Rate-limit counters live in each server's memory**, so on Vercel each instance counts separately. Fine at this store's traffic; move to a shared store (e.g. Upstash Redis) if abuse appears.
- **CSP allows inline scripts** (`'unsafe-inline'`), because Next.js and Google Analytics add inline scripts and a nonce-based policy would make every page uncacheable. All inline output is escaped, so this is defence in depth.
